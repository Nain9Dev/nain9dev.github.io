<div class="case-study-section" style="margin-bottom: 2rem;">
  <h2>El Problema</h2>
  <p>La plataforma SaaS sufría de tiempos de respuesta elevados (>2s) en horarios punta, con picos de carga que saturaban la base de datos principal.</p>
</div>

<div class="case-study-section" style="margin-bottom: 2rem;">
  <h2>Decisiones Arquitectónicas</h2>
  <ul class="case-study-list decisions-list">
    <li>Implementación de un sistema de caché distribuida (Redis) para consultas repetitivas.</li>
    <li>Partición de la base de datos (sharding) por tenant para aislar cargas.</li>
    <li>Migración de endpoints síncronos a procesamiento asíncrono con colas (RabbitMQ).</li>
  </ul>
</div>

  </div>
</div>

<div class="case-study-section" style="margin-bottom: 2rem;">
  <h2>Trade-offs</h2>
  <p class="case-study-tradeoff">Se aumentó la complejidad operativa (monitoreo de cachés, consistencia eventual) pero se logró escalar a 10x el tráfico sin degradar la experiencia.</p>
</div>

<div class="case-study-section results-section" style="margin-bottom: 2rem;">
  <h2>Resultados</h2>
  <ul class="case-study-list results-list">
    <li>Latencia reducida de 2.3s a 300ms (p95).</li>
    <li>Capacidad para manejar 50k peticiones concurrentes.</li>
    <li>Cero downtime en los últimos 12 meses (blue-green deployments).</li>
  </ul>
</div>
