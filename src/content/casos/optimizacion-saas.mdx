<div class="case-study-section" style="margin-bottom: 2rem;">
  <h2>El Problema</h2>
  <p>La plataforma SaaS sufría de tiempos de respuesta elevados (>2s) en horarios punta, con picos de carga que saturaban la base de datos principal.</p>
</div>

<div class="case-study-section" style="margin-bottom: 2rem;">
  <h2>Decisiones de Arquitectura (ADRs)</h2>
  <ul class="case-study-list decisions-list">
    <li><strong>Contexto:</strong> La base de datos SQL Server era el único cuello de botella; todas las consultas repetitivas de lectura golpeaban directamente a los discos.</li>
    <li><strong>Decisión:</strong> Partición de la base de datos (sharding) por tenant y uso de Redis como caché de primer nivel.</li>
    <li><strong>Alternativas consideradas:</strong> Migrar a NoSQL (descartado por necesidad de consistencia ACID en facturación).</li>
    <li><strong>Resultado:</strong> Descarga del 85% de las lecturas hacia Redis y operaciones de escritura asíncronas vía RabbitMQ.</li>
    <li><strong>Consecuencias:</strong> Mayor complejidad en la invalidación de caché y necesidad de monitoreo distribuido, mitigado con despliegues Blue-Green en Kubernetes.</li>
  </ul>
</div>

<div class="case-study-section" style="margin-bottom: 2rem;">
  <h2>Trade-offs</h2>
  <p class="case-study-tradeoff">Se aumentó la complejidad operativa (monitoreo de cachés, consistencia eventual) pero se logró escalar a 10x el tráfico sin degradar la experiencia.</p>
</div>

<div class="case-study-section results-section" style="margin-bottom: 2rem;">
  <h2>Resultados</h2>
  <ul class="case-study-list results-list">
    <li>Latencia reducida de 2.3s a 300ms (p95).</li>
    <li>Capacidad para manejar 50k peticiones concurrentes.</li>
    <li>Cero downtime en los últimos 12 meses (blue-green deployments).</li>
  </ul>
</div>
